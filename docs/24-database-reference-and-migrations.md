# Database Reference and Migration Specification

The [reference SQL](reference/schema.sql) defines the complete target baseline, including authorization, indexes, jobs, source provenance, automation, MCP, spending and cleanup. It is a design attachment, not an installed Flyway migration. Syntax parsing does not validate an actual PostgreSQL/pgvector deployment.

## Data ownership and constraints

Backend owns users, memberships, integrations, projects, job transitions, active-index selection, chat persistence, proposals, approvals, audit, outbox, spending and cleanup. Python writes source/chunk/vector data through a restricted role scoped to its authenticated job/generation. A worker must not acquire the general backend database credential. Enforce authorization at service boundaries and bound SQL statements; expose no arbitrary SQL tool.

All project-scoped rows carry workspace/project identity or an unambiguous parent foreign key. Composite foreign keys bind generations and source chunks to their project. Use UUIDs generated by the application; PostgreSQL defaults do not imply authorization. UTC timestamps use `timestamptz`. API enums and database checks must be changed together. Store source content only when it passes ingestion policy.

## Migration series

| Migration | Content | Forward/compatibility rule |
|---|---|---|
| V001 | Identity, workspaces, grants, integrations, projects | Deploy before protected features; no implicit project access |
| V002 | Jobs, leases, idempotency, events, outbox/deduplication | Enforce transaction boundaries before queue consumers start |
| V003 | Generations, files, chunks, vector tables | Install approved pgvector extension with DBA role; runtime role cannot install extensions |
| V004 | Conversations, messages, citation snapshots | Keep historical provenance when expired chunk rows are removed |
| V005 | Findings, proposals, approvals, tests, artifacts | Enable write features only after permissions/approval checks exist |
| V006 | MCP registry, tool execution audit, security audit | Registry starts disabled; no auto-enabled tools |
| V007 | Spend reservations, cleanup manifests, operational indexes | Backfill ledger/cleanup metadata before enabling associated quotas/deletion |

Generate actual migration files from reviewed schema sections in implementation, not by executing the entire reference file on an existing database. Each migration includes checksum validation, fresh-install and previous-release upgrade tests, lock-time measurement, and backup compatibility. Large indexes use a separately reviewed concurrent-build procedure; do not wrap unsupported concurrent operations in a transaction.

## Concurrency and access

Use row locking/compare-and-set for job claim, current desired generation, approval consumption, and budget reservation. Maintain a single active indexing lease per project using service transaction logic plus database uniqueness where applicable. A partial unique index prevents simultaneous active INDEX jobs; manual retry creates a new row after terminal state. Explicit permission bits supplement role; no role string comparison grants unrelated actions.

Initial exact search filters canonical project/generation before distance ordering. Parameterize SQL and constrain dimension/model compatibility. Pinecone results are mapped back to canonical chunk IDs and ownership checked. If active index changes during an answer, continue the captured generation or fail explicitly; never mix generations silently.

## Deletion and backup reconciliation

Project tombstone, epoch increment and cleanup request are committed together. Cleanup deletes remote vectors/artifacts before final local manifest completion; retries record per-resource outcomes. Historical citations retain path/SHA/range snapshots while chunk/file foreign keys are nullable on expiry. Conversation deletion removes content, not independently required financial/audit metadata. Retention follows [baseline policy](18-baseline-decisions-and-limits.md).

Restores must reconcile provider-side PRs, outbox publication, consumed events, leases and spend reservations. Never replay a restored approval as a fresh write authorization. Invalidate unconsumed approvals and internal execution tokens after restore.
